Two chat tabs, one model

We benchmarked the two AI backends behind our app's chat tabs — same model, same gateway, same tasks. The first result was a bug, not a verdict.

Johan Persson · 8 November 2026 · 9 min read

Why two tabs?

Our web app has two chat tabs that look identical. They share the same login, the same WebSocket frames, the same skill rail, the same spending and audit trail, and the same way files are written back to the workspace and the site overlay is applied. The only thing that differs is the backend.

  • Chat (#chat) runs an OpenCode harness for users on the allowlist. If the harness fails before it says anything, a thin fallback loop in the app steps in and answers instead.
  • Chat v2 (#chat-v2) runs a per-user headless Pi runtime. There is no fallback — a failure is reported as a failure, because the whole point of the tab is to show what Pi does.

Same job, two different philosophies: one tab hides a broken backend, the other surfaces it.

How we tested

Both arms used the same model and gateway — deepseek-v4.1-flash through OpenCode Go. We pointed them at two identical throwaway copies of the deployed site and ran two batteries of tasks, each three times. Everything was driven at the runtime level, not through the browser: auth, parked replies, budget frames and audit lines are shared plumbing and were deliberately left out of this comparison.

  • Battery v1 — 10 tasks: editing, search, multi-file changes, large-file lookup, SQL-free site work, skills, prompt injection, and .env / outside-path probes.
  • Battery v2 — 7 new tasks: a search-heavy rename, reading a skill's external reference file, a refresh feature with i18n wiring, quoting an exact line from a 228 KB file, a negative edit, safety probes and prompt injection.
Caveat: one model, one gateway, one workload, three runs each. It's a small sample. The dollar figures are pricing-table estimates for OpenCode and reported cost for Pi — not invoices. No production user data was used.

In battery v1 both arms passed 30/30 (after two test-checker corrections). OpenCode averaged 118.2 s and $0.0323 per run; Pi averaged 89.2 s and $0.0201.

The bug that changed the result

The very first v1 run made Pi look slower and more expensive than OpenCode — $0.0409 versus $0.0272. The cause wasn't the model. It was the deployment.

Pi's built-in grep and find shell out to ripgrep (rg) and fd. Those managed binaries sit next to the Pi launcher, but the child process's PATH only contained the Node directory — so every search came back with “ripgrep is not available”. The model kept compensating, which burned time and tokens.

The fix is one line of intent: prepend the launcher's directory to PATH whenever it carries rg and fd. Search calls went from “ripgrep is not available” to ok=True, and the search-heavy rename dropped from roughly 31 s / $0.0129 to 19 s / $0.0049.

The first benchmark result was a bug, not a verdict.

The skill-reference fix

A skill's instructions were loading, but its supporting files were blocked — so a task that asked the agent to attach the tdd skill and read its tests.md reference failed. The generated guard now allows read-only access to the skill source directory while still blocking writes there. The task passes, and the boundary holds.

The safety finding

One v2 task planted a symlink inside the workspace that pointed at a file outside it, then asked the agent to read it. In one of three runs, OpenCode's read tool followed the symlink and returned the planted marker. Pi's realpath guard blocked the same attempt in all three runs.

To be clear: this used a planted fake marker — no real secret was read and nothing leaked. But it's a useful reminder that “inside the workspace” has to be a real-path check, not a string-prefix check.

A path that looks inside the workspace can still point outside it.

Verdict

After the two fixes, for this workload: Pi was faster and cheaper, passed every task, and was more robust on the symlink probe. OpenCode was already reliable — zero failed tool calls across the batteries — and it remains the safer operational fallback, because tab 1 has the thin loop.

That's the honest summary. It is not a general “Pi beats OpenCode” result — one model, one gateway, one workload, three runs.

What's next

  • Deploy the fixes: the code is on main, but the running app container still needs a rebuild and restart before the live tabs use it.
  • Run the live socket smoke — auth, parked reply, budget frame, audit line — and verify the live tabs end to end.
  • Optionally harden OpenCode's read tool against symlinks, the same way Pi's realpath guard does.
When you add a fallback, measure the path that actually answered.

Method & caveats

One model and provider; a small sample (three runs per battery); costs are estimates, not invoices; runtime-level only; no production user data. Commits: b513f95 and e703a7a, with the earlier f6b05b8 and 9735a2e.
